---
title: Browser extension
description: Fill and save logins from the vault in Chrome and Firefox.
---

`apps/extension` is a Manifest V3 extension for Chrome, other Chromium
browsers and Firefox 128 or newer. It uses the web app's `lib/crypto` module,
so it reads and writes the same vault.

<Callout type="info">
  The vault itself is created in the web app. The extension signs in and
  unlocks an existing one.
</Callout>

## Build and load

```sh
pnpm build:extension   # writes apps/extension/dist/chrome and dist/firefox
```

- **Chrome**: open `chrome://extensions`, enable Developer mode, choose
  **Load unpacked** and pick `apps/extension/dist/chrome`.
- **Firefox**: open `about:debugging#/runtime/this-firefox`, choose
  **Load Temporary Add-on** and pick `apps/extension/dist/firefox/manifest.json`.

The two builds differ only in the manifest: Chrome runs the background script
as a service worker, Firefox as an event page with an add-on id.

## Pointing it at a server

The extension needs the **origin** of the server, such as
`https://pass.example.com`; it adds `/api/v1/…` itself. The defaults come from
`apps/extension/.env` at build time (`VITE_DEFAULT_API_URL` and
`VITE_DEFAULT_APP_URL`) and both can be changed under **Settings**. In a
deployment where the server also serves the web app, the two are the same URL.

The API accepts extension origins without a CORS entry.

## The popup

After signing in and unlocking, the popup shows:

- **Logins for the current site**, each with a **Fill** button.
- The whole vault, with search, a sort toggle and buttons to copy the username
  or the password.
- **Add**, to save a login for the current site, with a password generator
  (20 characters by default).
- **Full screen**, which opens the vault in a tab.

## Full screen

The tab view has three columns: filters (all items, logins, secure notes,
favorites), the list, and the selected item. Passwords stay hidden until
revealed. Items can be created and edited here, including their folder.

Sharing, folders, favorites and the trash are managed in the web app.

## When Fill is offered

A saved login is offered for a page when the page's host equals the saved
host, or is a subdomain of it. `www.` is ignored on both sides.

| Saved URL | Page | Offered |
| --- | --- | --- |
| `example.com` | `login.example.com` | yes |
| `login.example.com` | `example.com` | no |
| `example.com` | `example.com.evil.net` | no |

By default the extension reads no page on its own. It touches the active tab
only when **Fill** is clicked, and fills only visible username and password
fields. The [inline menu](#the-inline-menu) changes that, and is off until it
is turned on.

## The inline menu

**Settings → Show Montara Pass in login fields** puts a badge inside the
focused login field. Clicking it, or pressing <kbd>Alt</kbd>+<kbd>↓</kbd> in
the field, opens a menu under the field with the logins saved for that site;
picking one fills the form.

Turning it on asks for access to every site, because a content script then
runs on each page to find its login fields. Turning it off gives that access
back. Tabs that were already open need a reload to pick up the change.

| Piece | Where it runs | What it can see |
| --- | --- | --- |
| `content.js` | the page, top frame only | the page's fields; nothing from the vault |
| `inline.html` | a frame of the extension's own origin | the unlocked keys and the logins for the site |

The page around the menu can neither read the frame nor script it, and the
content script never receives a password: the frame fills the form itself,
the same way the popup does. The frame learns which site it is on from the
browser's record of its tab, not from the page.

A field gets the badge when it is a password field, a text field in a form
that has one, or a field marked `autocomplete="username"`.

<Callout title="Clicks a page tries to borrow" type="info">
  Before filling, the menu checks that it is fully opaque, on top of the page
  and still on a site the login matches, and it ignores clicks in its first
  300 ms. The menu sits in the browser's top layer; an overlay placed there
  after it that lets clicks through is not detected.
</Callout>

While the vault is locked the menu lists nothing and offers **Unlock**, which
opens the popup.

## Where secrets are kept

| What | Where | Cleared |
| --- | --- | --- |
| Access and refresh tokens | `chrome.storage.local` | on sign out |
| Unlocked vault keys | `chrome.storage.session` (in memory) | after 15 minutes without use, when the browser closes, on **Lock** |
| Master password | nowhere | used once to unlock |

## Permissions

| Permission | Why |
| --- | --- |
| `storage` | Tokens, settings and the unlocked keys |
| `activeTab`, `scripting` | Fill the page the user is looking at, on click |
| `alarms` | The auto-lock timer |
| `clipboardWrite` | Copy buttons |
| Host permission for the API | Call the API it was built for |

Another API origin, set under **Settings**, is requested from the optional
host permissions at that moment. So is every site, when the inline menu is
turned on.

For Firefox the manifest also declares what leaves the browser
(`data_collection_permissions`): authentication information and personally
identifying information. That covers the sign-in email and password sent to
the API and the encrypted vault stored there. Firefox 140 and later show it
when the extension is installed.
