---
title: Migrations
description: Changing the database schema with the embedded migration CLI.
---

SQL migrations live in `apps/server/migrations` as numbered `up` and `down`
files. They are embedded in the binaries, so a deployed image carries its own
schema.

## Commands

```sh
pnpm migrate:up                                              # apply what is pending
pnpm --filter @montara-pass/server run migrate:create add_x  # new up/down pair
pnpm --filter @montara-pass/server run migrate:version       # current version
pnpm --filter @montara-pass/server run migrate:force 2       # after a failed migration
pnpm migrate:down                                            # roll back everything
pnpm --filter @montara-pass/server run migrate:refresh       # down, then up
```

The CLI reads `DB_DSN` from the environment or `apps/server/.env`, or takes
`--db-dsn`.

<Callout title="down and refresh delete all data" type="error">
  `down` rolls back **every** migration, users included. Both commands refuse
  a database that is not on localhost unless `--allow-remote` is passed.
</Callout>

## On boot

With `MIGRATE_ON_BOOT=true` the API applies pending migrations before it
starts serving. With `SEED_ON_BOOT=true` it also creates the `SUPER_USER`
account, or brings it back to that password; running it again is harmless.

## Cloud Edition migrations

`apps/server/migrations/cloud` holds the tables only the Cloud Edition has.
They keep their own version in `schema_migrations_ee`, run after the main ones
and roll back before them. A Community Edition build never applies them, so
its database has none of these tables; a database that moves to the
Cloud Edition gets them on its next `up` or boot.

`up`, `down`, `refresh` and `version` act on both tracks. `force` and `create`
act on the main one unless `--cloud` is passed:

```sh
go run ./cmd/migrate --cloud create add_x   # new pair in migrations/cloud
go run ./cmd/migrate --cloud force 1        # after a failed Cloud migration
```

| Version | What it creates |
| --- | --- |
| `000001` | billing: `plans`, `subscriptions`, `purchases` |
| `000002` | Lemon Squeezy: `plans.variant_id`, `subscriptions.provider_subscription_id` |
| `000003` | Lemon Squeezy catalog and customers: one plan per `variant_id`, `users.provider_customer_id` |

Only an account with the `user` role holds a subscription or a purchase. The
database enforces it: both tables reference `users (id, role)` with the role
fixed to `user`, so a super user cannot subscribe, and a subscriber cannot be
given another role. Each table also takes only its kind of plan (`recurring`
or `one_time`), and a user has at most one live subscription.

## Tests against a real database

`apps/server/cmd/api` has an integration test that drives the API end to end.
It is skipped unless `TEST_DB_DSN` points at a PostgreSQL 18 database it is
allowed to wipe.

With `TEST_REDIS_URL` as well, that test keeps its rate limit counts and
idempotency keys in Redis, and `apps/server/internal/middlewares` runs its
Redis tests: two replicas sharing one budget, one answer and one lock. They
are skipped without it. Point it at a database number nothing else uses, such
as `redis://localhost:6379/15`.
